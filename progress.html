还欠什么 ​

  1. 人眼判决（协议 3）没收到。数字门全部通过后，"这就是森林 boss 房、纹理是对的、比例是对的"这一句 必须由人看图判定，量具不代替它。素材在 画面证据 的前两节（验收 ROM 三张 + 七张拼图）， 其中 contact_sheet_2026-10-05_final.png 是终检图：四格各只问一件事（整场景 / 本体被 Link 挡住 像不像 / 走到位后比例与四肢 / 转的是相机不是重画场景），一票判完不必翻其余六张分项。
  2. 偏差 4 会被人看见：本轮按计划不做相机碰撞，房间小、CAM_DIST=90 而眼高只有 60 ⇒ 5975 个合法站立格里 四个朝向各有 50~55% 让眼点落进极近几何档，那个档里量具与真机对不齐（色场 WARN 的来源）。
  3. 偏差 1 的归属未证：desmume 相对 CPU 量具的屏幕错位不是恒定 +3px（y180 最优是 dx=0）， 本体那四个独立读数倒是都落在 dx=2。glGetFixed 回读在 desmume 上不响应 ⇒ 上真机第一件事就是复测这条。
  4. 角色纹理两处以决定为由关掉：本体 draw_boss.c 只走顶点色 + 白纹理单位元，所以幻影加农在画面里发白； 场景里的 Link 走 src_scene/link_rigid.c，在 LINKTEX=1 之前同样只绑白纹理、不发 UV，所以林克也发白。 object_gnd 的骨架可达 limb DL 里实测有 51 SETTIMG / 51 LOADBLOCK / 51 SETTILESIZE / 102 SETTILE / 52 SETCOMBINE （且这是下界：每条 limb DL 那条外部段 G_DL 按既有口径不递归），要补得走与房间同套管线的另一份口径； Link 那侧则不缺料（17 张 CI4 + 每组 tex_id/UV 都在盘上），缺的是把 src/link_full_render.c 那条链搬过来， 搬完了但默认没开（开了就是换验收实物）。两条的完整口径与实测数在 五条已知偏差 偏差 2。 ⚠ 本页此前抄的是「190 / 97 / 54」，那是整镜像朴素 opcode 直方图把数据字节数成命令的结果，已由 docs §5 更正。
  5. 偏差 5 也会被人看见：把 Link 走到竞技场沿上，他站住不动而不是掉下去 —— 本轮不做重力，落点的地板 探测窗口是 [feetY, feetY+6]（src_scene/main.c:605，下界正好等于当前脚底），所以任何比当前脚底低的地面 一律被拒、整次移动作废。计划 S5 只要求"站在地面、撞墙不穿"，没要求 fall 状态，所以这是裁剪口径而不是 地板解漏了多边形。图上认这条看的是副屏坐标数字停住、walk 那对极值不再扩大，不是状态词 —— 截图前必然松键， 而 moveState 每帧在按键检查前复位，存档图里那个词恒为 idle（[feetY, feetY+6] 这条窗口的实测范围与配方在 五条已知偏差 偏差 5）。

演示录屏（2026-10-06） ​

ROM 自己演，不用手按：DEMO=1 每帧合成一个按键掩码喂给同一条行走/相机链（src_scene/main.c 的 s_demo[] 剧本：走进竞技场 → 相机转 180° → 再前进 → 回转 270° → 抬头 → 压低看本体 → 原路退回， 循环）。注入点在 START 退出判据之后，所以你碰任意键它就让出控制权，演示不是第二条没人验过的代码， 走的位置由同一份碰撞与同一步长决定。

  • 录屏 ROM：demoMori.nds = a583e3a0，配方 make -s SCENE=moribossroom WALK=1 BOSS=1 STARTX=15 STARTZ=-2900 CAMYAW=0.0 CAMPITCH=-5.0 DEMO=1 LINKTEX=1 NAME=demoMori（60 fps 口径；无头 desmume 开 --disable-limiter 会比这个快）。
  • 动图由单个 desmume 实例连续抓 30 帧拼成（相邻帧间变化 31k~46k / 49152 px，29 对里没有一对静止 ⇒ 确实在动，不是同一张图重复）。想拖动进度看细节：MP4 版（397 KB）。
  • 这台同时带 LINKTEX=1，所以下面那条 Link 纹理的修复在动图里是看得见的。

进度记录 2026-10-06（本轮最后一次实测，不重复上面的数） ​

  • Link 在场景 ROM 里本来就没有纹理（2026-10-06 发现并修）：src_scene/link_rigid.c 整条路只绑 白纹理单位元 + 逐部位纯色，一次 glTexCoord2f 都没发 —— 而 include/link_tex_groups.h 里每组的 tex_id 与每顶点的 UV 一直都有，只是没人用（独立 ROM src/link_full_render.c 用的是完整那条链， 所以"林克有纹理"在旧交付里成立、在场景 ROM 里不成立）。新旋钮 LINKTEX=1 接上：上传 17 张 RGBA （与 texInfos[] 同序，那是 tex_id 的编号契约）、逐组绑定（房间那条路的教训是整条 DL 只绑 一次会让后半段拿前半段的纹理）、纯色组继续走白纹理、逐顶点发 UV、glPolyFmt 加 POLY_MODULATION。 实测 lkSceneTex.nds = 83bd4dfa：同机位与锚点逐像素比差 530 px，差异 bbox x112–149 / y149–191 —— 正好是 Link 的剪影，房间与本体一个像素没动；LINKTEX 不传时锚点重编仍是 dd9bfa50。 交付 ROM 默认没开它（开了就是换验收实物），要不要转正等你决定。
  • 眼包素材的一处缺陷：偏差清单以前只记了「本体无纹理是范围决定」，没记「场景里的 Link 无纹理」， 画廊的"不算缺陷"列表里也没有 —— 于是看图的人只能得出"该有纹理的地方是糊的"。这条已经落到唯一上游： docs/scene-port.md §5 偏差 2 现在同时写明两处角色纹理的状态，五条已知偏差 那页由它再生。
  • 眼包自己的血统规矩补齐：_persp 前三格背后的三台变体 ROM（lkTexW b68af78a / lkTexFar 7f6c5831 / lkBxFar d8e6f4d3）此前从没按现源码逐位复现过 —— 按"每张图的前缀必须能用当前源码逐位复现"这条规矩， 那三格当时不算验收 ROM 的证据。今天整套照抄旋钮、逐台 rm -rf build/<NAME> 重编，三台全部逐位相同； lkBxFar 另做了 LINKDRAW=0/1 双产物交叉验证（第二次正好命中在册预测的 bde1a5a1），说明重建出的旋钮 集合唯一，不是碰巧对上。命令与结果逐字记在 evidence/eye/manifest.txt。这三台不在逐位复现名单里， 把它们加进去属于扩门，留给用户点头。
  • 发布面 == 在册实物：线上 8 张拼图逐张与 evidence/eye/ 里的同名文件比字节，8/8 相同。这是"你可以 直接在页面上投票"的前提 —— 你看到的画面就是被复现过的那份 ROM 画出来的。第一遍有一张取回 0 字节（网络侧 偶发，重取即 200 且 md5 一致），别读成"线上缺图"。
  • 判读口径改了两处，都是"别让评审人投出假 FAIL"：_persp/终检里"本体没有纹理"是本轮的范围决定而不是缺陷 （src_scene/boss 那条链路只走顶点色）；终检第 1 格原写"整场景对不对"，但实测那个机位下入口房在相机背后 （离线量具印它 0 px，而竞技场那间 49143 px），副屏那栏 GPU 1018/1018 是"两间全量提交、未剔除"，不等于 "两间都看得见"。
  • 仍然没闭合的只有一件事：协议 3 的人眼判决。机器侧四条协议都有当轮实测，但"这就是森林 boss 房"这句话 不能由量具自己说。另有两项等你决定：tools/measure_walk.sh/measure_fps.sh 是删掉还是给 ROM 加一条机器 可读输出通道（现 emulator 不转发宿主 printf），以及上面那句扩门。
