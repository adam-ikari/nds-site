1. 范围 ​

批准的终点是**「一个房间可自由走动探索（裁剪版）」**，具体到本场景 = 静态场景 + 幻影加农本体（静态网格）

  • Link 可行走。不做：跨房间 exit、水/WaterBox、boss AI 与战斗、bgCam 分区变相机（本轮固定相机 + D-pad 手控）、N64 原版参考截图管线。

⚠ 那一句「不做 boss AI 与战斗」是扩张前的边界：2026-10-11 用户把终点扩成做一场能演示的 boss 战斗 （project brain 的 boss-combat-scope-expansion 页，kind: reversal），M-combat-1（持剑/命中/挨打反应）已于 2026-10-12 收口、M-combat-2（血量与死亡链）正在做，实物与门在 §3 末尾那两段与 §4 的 M-combat 行。其余四项 （跨房间 exit、水/WaterBox、bgCam 分区变相机、N64 原版参考截图管线）不在扩张范围内，仍然不做。

本体身份钉死过一条误判：object_sst 是 Bongo Bongo（影之神殿），幻影加农是 actor type 0x52 → object_gnd，Standard 骨架（不是 Flex）⇒ 运行时 FK 不在本场景的依赖里。

2. 数据流 ​

external/oot/build/OoT.bin (ROM 权威镜像)

   ├─ tools/col_extract.py       → include/scene/col_mori.h            (地板/墙/天花板多边形, 分类阈值 NY_STEEP=16384)
   ├─ tools/scene_cmds.py        → include/scene/env_mori.h            (灯光/雾/PLAYER_ENTRY)
   ├─ tools/boss_extract.py      → include/scene/boss_gnd.h            (本体刚体网格)
   └─ scripts/room_tex_decode.py → include/tex_room/*.h                (CI8 → A1B5G5R5, 描述符只从 DL 解, XML 里没有纹理)
                data/*.json ── scripts/room_extract_c.py ─→ include/scene/room_mori_r{0,1}.h

房间文件本身就是场景命令表（无固定头），顶点在房间内已是世界坐标（G_MTX 计数 = 0），因此不需要房间矩阵， 也不需要角色侧那套段 0x0D Mtx 槽。段内寻址掩码是 & 0xFFFFFF（段 3）——scripts/f3dex2_extract.py 旧写法 & 0x1FFFFFF 只对偶数段侥幸正确，已修并回归。

3. 构建 ​

make -s                                        # 默认: 角色 ROM link_full_render.nds (锚定 8a546db4)
make -s SCENE=moribossroom WALK=1 BOSS=1 \
     STARTX=15 STARTZ=-2900 CAMYAW=0.0 CAMPITCH=-5.0     # 验收 ROM moribossroom_render.nds (锚定 83bd4dfa)

命中与反应那一族（M-combat-1，2026-10-12）：SWORDHIT=1 打开世界空间的刀身线段 vs 本体 440 面判定， 按 (anim,frame) 变化沿推进（一行判一次 ⇒ 钉帧配方读到的就是那一行的判词），活跃窗是攻击表行 1..4 （linkBladeSeg 窗外直接返回 0，与"没中"是两件事）。副屏印 hit N first F h H n N 而不印坐标：门比的是 布尔量，坐标会诱使"看着差不多就过"；n（本行真跑过的线段-三角测试数）把 h=0 分成"比了没中"与"根本没比"。 BOSSREACT=1 把本体换成从反编译 z_boss_ganondrof.c 移植的那台两支状态机（第一下 AirDamage + timers[0]=50、 反应中再挨 GroundDamage 且不重置计时、GND_INVINC_TIMER=10 无敌期内的 AC_HIT 直接吞、计时到 0 回待机）， 段表是另烘的一张 include/scene/boss_anim_react.h（八段 IDLE/AIR/GND/STUN + S2 烘进来的 DEATH/LIMP/SCREAM/POSE 四段死亡链，段号 4..7；⚠ 段号换义：反应表打开后 BOSSSEG=1 不再是投掷段）。BOSSWIND=<n≥0> 把链冻在走完 n 个动画 tick 那一格，BOSHHITAT='{a,b,…}' 在第 a、b…个链 tick 上替 ROM 的 CollisionCheck 按一下（激励注入不是新机制，它不新增任何状态； 花括号必须单引号包住整值，否则 shell 把它展开成两个词）。四枚默认全关/空 ⇒ 三枚锚点逐位不变。 冻窗买的是"读数与快门落点无关"这句话：副屏自印 react b<i> t<timer> w<tick> 里那个 w 就是设备自报走到第几格， 抓图回路（tools/react_sweep.sh）拿它与配方的 BOSSWIND 对账，落在冻住之前的图直接重拍（口径与实测反例见 evidence/sword_react/manifest.txt）。

血量与死亡链那一族（M-combat-2 S1/S2）：BOSSHP=<n>（默认 30 = ROM Init:309 的 colChkInfo.health） 把起手血量钉成编译期常量，BOSSDSTAGE='{150,350,50,40,250}'（默认就是 ROM Death() 那五格 stage 计时： :1008/:1043/:1082/:1109/:1119）把死亡链的长度也钉成常量。两枚旋钮都存在同一个理由上，后一枚的理由更硬：WARP 那 350 格里本仓库只有一件事在动（帧号在 Limp 上绕圈），走满它要二十分钟无头模拟且不产新信息 ⇒ 在册证据里 THROES 的 150 用 ROM 原值现证（dthWarpRom 恰好落在边界那一格：r=0 而 d 还是 1），后面四段用缩短值 证机制。这句话是"哪一台量哪个数"，不是"某几格可以不核"。移植的算术在 CollisionCheck:1276-1287： dmg=2（大师剑）、(dmg==0)?dmg=2:canKill=true、if (health>2 || canKill) health-=dmg、 health<=0 ⇒ SetupDeath + return —— 那句 return 的意思是血尽那一格不进 Stunned，所以段号是 DeathBlow 而不是 AirDamage，这是 dthKill 那台量的东西。死亡链的 tick 里 ROM 不跑 CollisionCheck（Update:1347）⇒ 死亡期的注入击是空操作（dthPost）；同一条理由决定 i 在整条死亡链上不动（那条减在 :1253，也在 CollisionCheck 里）⇒ 各台死亡图的 i 恒 0 是自证不是巧合。killActor（:1148）在下一 tick 的 Update 首行 Actor_Kill（:1326）⇒ bossAnimDraw 早退，副屏那行的三角形数变成 BOSS 0/440 —— "屏幕上真的没有本体了" 这句由设备自己说，不由一个被置起来的变量说。读数因此分两行：react b/i/t/w 与 dth h/d/g/s/r，理由是 副屏控制台只有 ~32 列（实测折行点），九格写一行会把最后一格劈成半截、门就解析不出来了；G5 那四格留在上一行 ⇒ 在册的反应链图仍然可解析。量具是 tools/boss_death_gate.py（离线把同一台整数状态机在 Python 里另走一遍； 配方表只在这一边）与 tools/death_sweep.sh（造图，它向门读配方与"该走到第几格"，不抄第二份 —— 消失那台 的 w 永远小于 BOSSWIND，按 wind 等会白等四次）。

这一片动的是 #if BOSSREACT 之内那条链，所以它把已有的十二台一起推动了字节：反应链七台（rct*）与 反应段姿势五台（rp*）全部重连重拍，读数与像素都不变（七台五栏逐字相同；五台上屏 0/49152 逐像素 相同，副屏各差 395 px，全部落在新印的那行 dth h… 上）⇒ 这次重锚换的是"这台机器是谁"而不是"这一格 量到什么"。同一轮里三台默认锚点与命中链十台逐位不变，是"改动被旋钮挡在交付 ROM 之外"那句的负方向实物。 还有一条边界要说清：姿势那五台仍只钉段 0..3，而死亡链这十四台拍的是副屏（death_sweep.sh 的 SCREEN=sub，目录里十四张全是 *_sub.png）⇒ 段 4..7（DeathBlow/Limp/Scream/LastPose）既没有逐顶点姿势 对账，也没有上屏实物。这一族说的是时序与状态：血、无敌、五格 stage、deathState 推进、killActor； 其中"本体消失了"那句由设备自印的三角形计数说（dthGone 那台 BOSS 0/440，其余 BOSS 440/440），那是 读数不是像素。要补的是两件事：一档 BOSSSEG=4..7 的钉帧孪生（量具不改，它的段数已经从表里的 #define BGR_NANIM 现读），以及给人看死亡姿势时的上屏（SCREEN=both）。

位移链那一族（M-combat-2 S3a）：BOSSFLY=1（默认 0）把本体的位置与朝向从"编译期常量 BOSS_X/BOSS_Z 加一次 colFloorY 探针"改成交给 ROM 那台状态机 —— z_boss_ganondrof.c 的 Neutral:507 悬停、Stunned:757 摔落、Death:962 抬升与钉位，每 tick 一组单精度算式。这枚旋钮存在的 理由与 LINKTEX 那一类不同：它不是"加一条通路"，而是把已在册的那批图换掉输入。本体位置是剪影类 （bSil*）、动画类（bA*）、命中链（hit*）每一张图的自变量，位置一动那些读数就全都不是原来的了 ⇒ 默认必须落回 0，且调用点是复制出来的整行而不是改原行。本轮的负方向实物：dthWarpRom 在位移节落地后 重编仍是 b53d6e77，三枚锚点仍是 8a546db4/83bd4dfa/550345a4。

一条构建纪律钉死了实现的位置：那一节住在 src_scene/draw_boss.c 的 #if BOSSFLY 之内，不是src_scene/boss_fly.c。理由是实测：src_scene 下新增一只编译单元，哪怕它编译成空的 .o，也会挪动链接 布局 —— 锚点 83bd4dfa 跑成了 cf558ede。同一句纪律的另一半是"不许为 BOSSFLY 引入 #if 之外的新声明"： 第一版为了只在推进那一格认领 timers[1] = 50（:1043）与 :1084-1087 的钉位，加了一只局部 int advanced，那句落在 #if BOSSFLY 外面 ⇒ 会挪动死亡链那十四台的字节。正解是把这两句照原式钉回 它们各自那条 case 里（它们本来就写在 ROM 那对花括号里），设备侧零新增语句。这个 bug 的现场是"整个 WARP 窗口每格都把 timers[1] 重新上弦到 50"：四台孪生的 u 栏设备恒比离线多 —— WARP 窗口里差的是"这一格已走 了几格"（flyWarp 在 k120 设备 49 / 离线 34，差 15），出窗之后差定在 29 = 窗口长 30 减 1（第一格那次 50→49 的减仍然发生）——"每格重上弦"吞掉的正是余下那 29 次减，而 u 是唯一会说这句话的那一栏。 而 boss_fly_gate.py 的 pin-late/no-pin 两档负对照就是为这一类相位错设的。

时钟相位那三句话是这一族最容易抄错的地方（比算式本身更容易）：yawTowardsPlayer 在 actor 还没动的时候算 （Actor_UpdateAll:2490 排在 actionFunc:1333 之前）；死亡链的位移夹在 stage 推进的两侧（:1034-1037 在推进之前，:1084-1087 在推进之后）；timers-- 全减、无条件、死亡期也减，且排在 actionFunc 之后 （Update:1335-1339）—— 所以 bossFlyTick / bossFlyEnteredStage / bossFlyTimers 是三只函数而不是 "一个 tick 一只手"。量具是 tools/boss_fly_gate.py（离线用 numpy.float32 把同一条单精度机器另走一遍， 血量与 stage 推进外包给 boss_death_gate.py 的 trace，两只门共用一条状态机而不各抄一份）与 tools/fly_sweep.sh（造图，命令与"该走到第几格"都向门读）。十三格读数分四行印，还是副屏 ~32 列那条限制： z 与 rot 都是五位带符号数，三个以上就把末格劈掉。

BOSSSEG=<段> BOSSFRAME=<帧> 与 BOSSWIND 买的是两件不同的东西，别混：前两位把状态机停住（段与帧成 了编译期常量，bossAnimTick 直接 return），于是"这一格机内算出什么"与时钟无关，那批图不需要冻窗； BOSSWIND 让链照自己的节奏走完 n 格再停，量的是那条链本身。停在反应表里哪一格、姿势数据对不对，由 boss_frame_gate.py --react 逐格量（五台实物与读数在 evidence/anim_boss_react/manifest.txt）。另有一条 编译期口径：钉住段号（BOSSSEG>=0）时 BOSHHITAT 那张注入表连声明一起挡在编译期外 —— 状态机不推进， 注入没有去处，那句话本来是空话，不该留下一张没人读的表。

这一轮抓到的是 switch 的语义而不是一只常数：ROM 的 CHARGE_START 那个 case（:855-860）没有 break，掉进 CHARGE_ATTACK。FALLTHROUGH 是 case 的形状，不是"换段那一格"的事件——整个 START 段 每一格都在跑俯冲的算式，而 work 槽还写着 START。离线镜像的第一版按直觉写成"换段那一格才 fallthrough"， 于是 speed 与俯仰在那八格里都是 0，整条出招链晚七格；设备在 k144 印 c1 m4 p-5604 sp16，它算出 c1 m4 p0 sp0。正解照 C 的语义每格往下掉，并把这一形状钉进 ROLE_EXPECT['chgstart']（sp>0 与 p!=0 必须与 c==CHG_START 同时成立）——光"两侧一致"不够，两侧一起错也是一致。负对照 chg-no-fallthrough （补上 break）撞 6 台。

通路对账要同树只差旋钮，归因要按整文件 md5 判：A/B 的正确构造是同一棵源码树上传不同旋钮集合，而不是 "改前 vs 改后"两次构建 —— 后者把无关的源码改动一起量了进去（48 px 那个旧读数就是这么来的：两张只活在 /tmp 的孤儿截图，配方没记进任何 manifest，从此不可重算）。判"哪一枚旋钮动了画面"不用数像素，直接比 PNG 整文件 md5：单开 FIXSUB 的构建与旋钮全关的构建出同一张图（md5 相同），单开 LITFIX 的与 FIXSUB+LITFIX 的出同一张图 ⇒ 结论是"提交位宽零代价、全部像素差属整数光照"，比"差 99 个里大概多少来自 光照"这种估算硬得多。同一枚配方在改动前后两个树根编出同一个 md5，还能顺带证成"默认通路逐位不变"这句话 在锚点之外的机位上同样成立。截屏侧的前提是钉帧（ANIMSEL/ANIMFRAME/BOSSSEG/BOSSFRAME 全给编译期 常量）：姿势钉死之后两台的上屏内容与墙钟无关，实测同一 ROM 重截与归档实物 0/49152 像素差。
