数据流与构建 ​

本页正文由 tools/gen_site.py 从 docs/scene-port.md §1–§3 原样搬来(唯一上游在那份文档里)。更长的设计蓝图在 docs/architecture.md,预算与可行性在 docs/feasibility.md,工具链在 docs/toolchain.md。

1. 范围 ​

批准的终点是**「一个房间可自由走动探索（裁剪版）」**，具体到本场景 = 静态场景 + 幻影加农本体（静态网格）

  • Link 可行走。不做：跨房间 exit、水/WaterBox、boss AI 与战斗、bgCam 分区变相机（本轮固定相机 + D-pad 手控）、N64 原版参考截图管线。

本体身份钉死过一条误判：object_sst 是 Bongo Bongo（影之神殿），幻影加农是 actor type 0x52 → object_gnd，Standard 骨架（不是 Flex）⇒ 运行时 FK 不在本场景的依赖里。

2. 数据流 ​

external/oot/build/OoT.bin (ROM 权威镜像)
   ├─ tools/room_extract.py      → data/moribossroom_room_{0,1}.json   (DL 走查: 顶点/三角形/纹理描述符/剔除位)
   ├─ tools/col_extract.py       → include/scene/col_mori.h            (地板/墙/天花板多边形, 分类阈值 NY_STEEP=16384)
   ├─ tools/scene_cmds.py        → include/scene/env_mori.h            (灯光/雾/PLAYER_ENTRY)
   ├─ tools/boss_extract.py      → include/scene/boss_gnd.h            (本体刚体网格)
   └─ scripts/room_tex_decode.py → include/tex_room/*.h                (CI8 → A1B5G5R5, 描述符只从 DL 解, XML 里没有纹理)
                data/*.json ── scripts/room_extract_c.py ─→ include/scene/room_mori_r{0,1}.h
                ROM 侧: src_scene/{main.c, draw_room.c, collision.c, link_rigid.c, draw_boss.c} + include/room_gpu.h

房间文件本身就是场景命令表（无固定头），顶点在房间内已是世界坐标（G_MTX 计数 = 0），因此不需要房间矩阵， 也不需要角色侧那套段 0x0D Mtx 槽。段内寻址掩码是 & 0xFFFFFF（段 3）——scripts/f3dex2_extract.py 旧写法 & 0x1FFFFFF 只对偶数段侥幸正确，已修并回归。

3. 构建 ​

make -s                                        # 默认: 角色 ROM link_full_render.nds (锚定 8a546db4)
make -s SCENE=moribossroom WALK=1 BOSS=1 \
     STARTX=15 STARTZ=-2900 CAMYAW=0.0 CAMPITCH=-5.0     # 验收 ROM moribossroom_render.nds (锚定 83bd4dfa)

SCENE= 非空时 Makefile 把 SOURCEDIRS 切到 src_scene/（src/ 与 src_scene/ 各有一个 main()， 混在一起必然重定义）。默认构建行为不受场景侧任何改动影响。

诊断旋钮（全部经 Makefile 白名单转发，不传即预处理后源码不变）： ROOM=（只画某间）ROOMS=0（一间也不画 ⇒ 清屏色变洋红，"非洋红像素"就是本体/角色的剪影， 本体门的实机侧就这么取）ROOMTEX=0（无纹理孪生）LINKDRAW=0 BOSS=0 WIREFRAME=1（按部位上色线框） LAYER=/XLUB=（opa/xlu 分层）TRICOLOR=/TEXONLY=/TEXRAMP= LINKBBOX=1（印 Link 投影包围盒） VRAMMAP=1（印纹理显存占用表）PROJDUMP=1（回读硬件投影矩阵，desmume 上不响应） PERSP=/YAW=/PITCH=/ZOOM=/EYEX|Y|Z=（正交诊断机位）CAMDIST=/CAMH=/STEP=/LINKYAW0=LINKSCL=/LINKCULL=/BOSSSCL=/BOSSCULL=/RAMSTAT=。 道具那一族只有一个旋钮：LINKSWORD=1（左手 limb 的 nearDL 换成 gLinkChildLeftHandHoldingMasterSwordDL， 624/697 变成 733/763 顶点/三角形）。它默认 0，所以两个验收锚点一字不变；它与 LINKANIM=1 互斥 （link_anim.h 按 624 顶点编号），两头都在 src_scene/link_rigid.c 里以 #error 钉死而不是靠文档提醒。 出处、像素差集读数与两个被抓住的缺陷在 evidence/sword/manifest.txt。 逐帧动画那一族：LINKANIM=1（Link 不再画 bind pose，改逐顶点乘 include/scene/link_anim.h 的累积矩阵） ANIMSEL=/ANIMFRAME=/ANIMHZ=；本体侧同一条形状 —— BOSSANIM=1/BOSSFORM=（0=gnd 幻影加农，1=gndd 青年加农） BOSSSEG=/BOSSFRAME=/BOSSHZ=。*_FRAME=/*_SEG=/*_SEL= 把段与帧钉成编译期常量不是为了玩：无头会话里副屏那行屏帧计数会饱和 （实测 SETTLE 从 2 s 加到 90 s 恒印 frame 60），画面却还在动 ⇒ 读数与画面不成对（evidence/anim_boss_device/manifest.txt 的"时钟探针"一节给了 137 px 这个数）。钉死帧之后读数与画面恒等，那种错位没有发生的余地。 BOSSFORM 的默认值与取值范围归 include/scene/boss.h 管（不是 draw_boss.c）—— 因为 main.c 也要在副屏 那行 BOSSA form … 里读它，谁在自己文件里 #ifndef 一份就多出第二份默认值，两处一旦分家，副屏自印的形态 与真正在画的那张表就不是同一件事（本轮就是这么撞出来的：main.c:668 'BOSSFORM' undeclared）。

性能通路那一族（2026-10-09 起，口径与实现注在 include/fix_perf.h）：FIXSUB=1 把顶点提交换成定点 （glVertex3v16 / glTexCoord2t16 —— glTexCoord2f 是 libnds 的非内联函数，每顶点都要 DynamicArrayGet 查一次当前绑定纹理尺寸再乘，videoGL.c:2152；glVertex3f 是三次 floattov16）； LITFIX=1 把逐顶点光照换成整数（法线 Q13 × 光向 Q14 → nd Q13 → 257 格 Q8 亮度表 → prim×亮度>>8， 饱和白送：lv≤256 且 prim≤255）；LITAUDIT=1 让同一个顶点再跑一遍浮点原式并逐位对账，它隐含 LITFIX （没有第二条路可比时本开关无意义，include/fix_perf.h 里以 #error 钉死）。三个默认全 0 ⇒ 不传就是已验收的 浮点通路，三枚锚点逐位不变。判据是副屏自印两行：fix mis 必须 0（定点提交 vs 浮点提交逐位对账，含 bossFixAudit 那条动画路位置核对）、lit max 是整数光照 vs 浮点原式的逐通道最大色差。为什么值得做：DS 的 ARM946E-S 没有 FPU，每个 float 运算都是 libnds 软浮点调用，而 src_scene/ 三条绘制路原本逐顶点都在做 浮点法线变换加 glVertex3f。归因矩阵（LITPROBE/CULLPROBE/VPSCALE 那三枚一次性旋钮）先定性：摘掉逐顶点 浮点光照 5.45→7.53 sf/s，组内 glEnd/glBegin 重启与把 3D 视口缩到 1/16 像素都免费 ⇒ 收费的是 CPU 侧 逐顶点算术，不是填充。

帧率必须周期锁定着量：bash tools/measure_fps_cycle.sh <ROM> [秒=90]（环境变量 DISP=/WARM=/POLL=）。 它把被测墙钟区间钉成整数个剧本循环：tools/demo_cycle.py 从 main.c 现算 DEMO=1 剧本长 765 屏帧， 副屏 frame 每 30 屏帧才重印 ⇒ 可比窗口长度取 lcm(30,765)=1530 屏帧 = 2 个循环的整数倍，起点相位任意。 ⚠ 固定墙钟窗口不可比，这不是洁癖而是实测：同一台 ROM 两个 60 s 窗口读出 4.08 与 15.63 sf/s —— 一个循环里相机从入口房走进竞技场、转身、抬头、看本体，每段可见几何量差很多，于是那量的是"这一段有多重"， 不是"这台有多快"。⚠ 另一种写死的办法（盯着某个目标 frame 等它跳到位）在帧率提上去以后自己会失效： 30 sf/s 时一次打印正好 1 s 一遇，与"截屏＋字形匹配"一轮同量级 ⇒ 必然越过目标值，越是变快越量不出来。 现在的做法是一路把 (时刻, frame) 采下来，结束后配所有相差 k×1530 的读数对取中位数；重复性实测 ±1.5%（45 个窗口 11.71~12.07 sf/s）到 ±0.1%（7 个窗口 39.39~39.45）。 读数（全部来自 desmume JIT，--disable-sound --disable-limiter；真机 ARM9 更慢 ⇒ 这是乐观的一侧； 参照系：N64 原版 OoT 本身就是 20 fps 的游戏）：全软浮点 550345a4 ≈ 227 ms/帧 → 房间+Link+本体全整数 25.4 ms = 39.42 sf/s，与"整数路＋摘掉本体"的 25.0 ms 只差 0.4 ms ⇒ 本体绘制从整帧 73% 掉到 1.6%。 配方、两侧实物的逐位复现、原始采样序列与逐像素对在 evidence/perf/manifest.txt。

通路对账要同树只差旋钮，归因要按整文件 md5 判：A/B 的正确构造是同一棵源码树上传不同旋钮集合，而不是 "改前 vs 改后"两次构建 —— 后者把无关的源码改动一起量了进去（48 px 那个旧读数就是这么来的：两张只活在 /tmp 的孤儿截图，配方没记进任何 manifest，从此不可重算）。判"哪一枚旋钮动了画面"不用数像素，直接比 PNG 整文件 md5：单开 FIXSUB 的构建与旋钮全关的构建出同一张图（md5 相同），单开 LITFIX 的与 FIXSUB+LITFIX 的出同一张图 ⇒ 结论是"提交位宽零代价、全部像素差属整数光照"，比"差 99 个里大概多少来自 光照"这种估算硬得多。同一枚配方在改动前后两个树根编出同一个 md5，还能顺带证成"默认通路逐位不变"这句话 在锚点之外的机位上同样成立。截屏侧的前提是钉帧（ANIMSEL/ANIMFRAME/BOSSSEG/BOSSFRAME 全给编译期 常量）：姿势钉死之后两台的上屏内容与墙钟无关，实测同一 ROM 重截与归档实物 0/49152 像素差。

⚠ "旋钮全 0 ⇒ 字节不变"有三种看着更干净的写法会破它（三条都在 550345a4 上实测过；判据是 diff <(gcc -S 改动前) <(gcc -S 改动后) 只差 .file 一行，不是"看起来没动")：① 把一条算术从表达式里提成 int 语句 —— static 且只有一个调用者的函数 gcc 必内联，于是"值什么时候落寄存器"改的是调用者的栈帧 （draw_boss.c 的 bossAnimXform 提了个 nn，bossAnimDraw 613 条指令原地重排）；② 为定点表下标引入临时量 —— 经由指针结构体取 R->tri[ti][v] 时索引值从寄存器改走栈槽，而同一条改写加在定长全局 boss_tri 上不 改字节，所以静息路与动画路写法不一样不是疏忽；③ 移动 #include 的位置 —— .text 一字不动，但 .rodata/.bss 的段发射顺序变 94 行。定下的做法：浮点原式只许整段搬进宏（BOSS_LIT_F / BOSS_NDOT， 宏不改调度），两条路各开各的定点表。link_rigid.c 里那处 int nn 提成语句没出事，是那条路的上下文恰好 不让调度变 —— 不可移植的经验，别当成许可。

抓图与按键驱动在截图脚本侧： SCREEN=top|sub|both bash tools/capture_screen.sh <rom> <out.png>（both 把同一张整窗图裁两次，副屏落 SUB_OUT=，默认 <out 去扩展名>_sub.png），环境变量 KEYS='Up=45,Right=2'（依次按住 N 秒）、 SETTLE=（副屏文字每 30 帧才刷新，键盘图至少 12）。 键盘驱动的图必须 SCREEN=both：--disable-limiter 下"按住 N 秒"走多远随机器负载变（实测同一条 KEYS 四次落在 z −3003/−2997/−3054/−2988，三下短按 A 只收到 2 下 —— 逐条记录在 evidence/eye/manifest.txt:246-249）， top 与 sub 分两次跑就是两次不同的会话 ⇒ 读数描述的不是那张画面，编译期孪生必然对不上（本轮真那样 FAIL 过四轮）。both 保证画面与读数同一瞬间， 之后 bash tools/walk_pose_proof.sh 自己读数、按读数建孪生、逐字节比（0/49152 才算这张行走图的站位机位被证明）。 ⚠ 但 both 保证的是"同一次截图"，不是"同一次刷新"：副屏文字只在屏帧计数 %30==0 那一帧重印，而这个计数 在无头会话里会饱和（实测 SETTLE 2 s→90 s 恒印 frame 60，同期上屏还在动 —— 数与配方在 evidence/anim_boss_device/manifest.txt 的"时钟探针"一节）。所以"这张图画的就是这一帧"只对把帧号钉成编译期常量的 孪生成立；按键驱动的图由 0/49152 那一步兜住 —— 读数与画面一旦分家，孪生必然对不上。

变体纪律：blocksds 的 Makefile 只转发上面这些白名单变量，且 CFLAGS 不是 make 依赖 —— 每个变体必须 rm -rf build/<NAME> 后单独传 NAME=，并且先核对产物 md5 变了再看它的输出。历史上踩过一次：加了 PROJDUMP 却忘了加转发行，镜像与上一个变体逐位相同，打印从未生效。

status:"deleted" / lifecycle:"deleted" （revision 1 → 2 → 3）、active_release_id:""、cover:null；list_sites 返回 total_size:0； 旧域名 phantom-ganon-nds-1hed6xxc0ho.qoder.website/index.html 实测 HTTP 404。⚠ 这种无扩展名 URL 必然 404，只有 .html 形式能用。产物推到公开仓库 adam-ikari/nds-site （只有构建物 + .nojekyll，无源码、无 ROM、无 external/），仓库必须 private:false —— 免费 plan 的私有仓库 开不了 Pages。⚠ .nojekyll 只存在于那个仓库、不在 dist/ 里，所以 rsync --delete 两个目的地并存那阵子，两份构建的先后顺序是有代价的：docs:build 把 dist/ 当成唯一输出目录，Pages 那份会原地覆盖私有那份，所以流程只能是「私有档 → 发布 → 子路径档 → 推 → 立刻重建私有档 → 再跑一次 --check-dist」，中间任何一步停下来留下的都是错味的 dist。⚠ 那句"发布排在子路径档之前"是硬约束不是建议，代价本轮真付过一次： 脚本链两份构建都以 rm -rf dist && cp -a .vitepress/dist dist 结尾，所以 SITE_BASE=/nds-site/ 那份一跑完， dist/ 里躺着的就是带前缀的产物（它不是临时目录，是发布目录）—— 那时再去 prepare_site 打包的就是它。 实跑记录：第一次发布的 artifact 33686727… 就是这份被污染的那只，--check-dist 报 213 处 /nds-site/ 命中， 重发 87358af0… 才纠正。规矩因此多一行：prepare_site 之前必须现跑一次 --check-dist，不靠记忆排序。 构建日志本身也要读，不能只看退出码：本轮想把子路径构建挪到 cp -a 出来的副本 + 软链 node_modules 里做 （怕污染真 dist），结果那次 vitepress build rc=0 却吐了 54 处 vitepress data not properly injected in app， 而原地构建两种档位都是 0 处（那 54 处的取法与"先删 .vitepress/cache 仍 54"的对照记在 brain 页 progress-site-single-upstream；盘上此刻还能复核的是反面 —— web/site/.vitepress/build.log 现读该串 0 处命中）。 所以 npm run docs:build 现在把日志落到 .vitepress/build.log 并用 ! grep -q 'vitepress data not properly injected' 挡住 —— 命中就不做后面的 cp -a .vitepress/dist dist，整条链 rc=1。 功率是拿那个副本实测的：vitepress build 自身 rc=0、日志 54 处命中 ⇒ 守卫拦住（先删 .vitepress/cache 再建， 仍是 54 处，所以病因是"在副本里建"不是缓存陈旧）。⇒ 结论：别在副本里建，两份产物都必须在 web/site 原地建。 站点字节刻意不列入逐位复现名单，这条是实测出来的而不是猜的：同一份上游连做两次默认构建， diff -rq 报 7 个 html 全部不同，app.*.js/theme.*.js/@localSearchIndexroot.*.js 三个 chunk 的文件名哈希也换了一遍 —— 本地搜索索引把 lastUpdated 时间打进 chunk 内容，文件名哈希级联跟着变。所以门里那 52 台逐位复现只算 ROM 与截图， 站点的可复现锚在上游：tools/gen_site.py 从 docs/scene-port.md 与
