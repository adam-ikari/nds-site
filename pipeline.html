数据流与构建 ​

本页正文由 tools/gen_site.py 从 docs/scene-port.md §1–§3 原样搬来(唯一上游在那份文档里)。更长的设计蓝图在 docs/architecture.md,预算与可行性在 docs/feasibility.md,工具链在 docs/toolchain.md。

1. 范围 ​

批准的终点是**「一个房间可自由走动探索（裁剪版）」**，具体到本场景 = 静态场景 + 幻影加农本体（静态网格）

  • Link 可行走。不做：跨房间 exit、水/WaterBox、boss AI 与战斗、bgCam 分区变相机（本轮固定相机 + D-pad 手控）、N64 原版参考截图管线。

本体身份钉死过一条误判：object_sst 是 Bongo Bongo（影之神殿），幻影加农是 actor type 0x52 → object_gnd，Standard 骨架（不是 Flex）⇒ 运行时 FK 不在本场景的依赖里。

2. 数据流 ​

external/oot/build/OoT.bin (ROM 权威镜像)
   ├─ tools/room_extract.py      → data/moribossroom_room_{0,1}.json   (DL 走查: 顶点/三角形/纹理描述符/剔除位)
   ├─ tools/col_extract.py       → include/scene/col_mori.h            (地板/墙/天花板多边形, 分类阈值 NY_STEEP=16384)
   ├─ tools/scene_cmds.py        → include/scene/env_mori.h            (灯光/雾/PLAYER_ENTRY)
   ├─ tools/boss_extract.py      → include/scene/boss_gnd.h            (本体刚体网格)
   └─ scripts/room_tex_decode.py → include/tex_room/*.h                (CI8 → A1B5G5R5, 描述符只从 DL 解, XML 里没有纹理)
                data/*.json ── scripts/room_extract_c.py ─→ include/scene/room_mori_r{0,1}.h
                ROM 侧: src_scene/{main.c, draw_room.c, collision.c, link_rigid.c, draw_boss.c} + include/room_gpu.h

房间文件本身就是场景命令表（无固定头），顶点在房间内已是世界坐标（G_MTX 计数 = 0），因此不需要房间矩阵， 也不需要角色侧那套段 0x0D Mtx 槽。段内寻址掩码是 & 0xFFFFFF（段 3）——scripts/f3dex2_extract.py 旧写法 & 0x1FFFFFF 只对偶数段侥幸正确，已修并回归。

3. 构建 ​

make -s                                        # 默认: 角色 ROM link_full_render.nds (锚定 8a546db4)
make -s SCENE=moribossroom WALK=1 BOSS=1 \
     STARTX=15 STARTZ=-2900 CAMYAW=0.0 CAMPITCH=-5.0     # 验收 ROM moribossroom_render.nds (锚定 dd9bfa50)

SCENE= 非空时 Makefile 把 SOURCEDIRS 切到 src_scene/（src/ 与 src_scene/ 各有一个 main()， 混在一起必然重定义）。默认构建行为不受场景侧任何改动影响。

诊断旋钮（全部经 Makefile 白名单转发，不传即预处理后源码不变）： ROOM=（只画某间）ROOMS=0（一间也不画 ⇒ 清屏色变洋红，"非洋红像素"就是本体/角色的剪影， 本体门的实机侧就这么取）ROOMTEX=0（无纹理孪生）LINKDRAW=0 BOSS=0 WIREFRAME=1（按部位上色线框） LAYER=/XLUB=（opa/xlu 分层）TRICOLOR=/TEXONLY=/TEXRAMP= LINKBBOX=1（印 Link 投影包围盒） VRAMMAP=1（印纹理显存占用表）PROJDUMP=1（回读硬件投影矩阵，desmume 上不响应） PERSP=/YAW=/PITCH=/ZOOM=/EYEX|Y|Z=（正交诊断机位）CAMDIST=/CAMH=/STEP=/LINKYAW0=LINKSCL=/LINKCULL=/BOSSSCL=/BOSSCULL=/RAMSTAT=。

抓图与按键驱动在截图脚本侧： SCREEN=top|sub|both bash tools/capture_screen.sh <rom> <out.png>（both 把同一张整窗图裁两次，副屏落 SUB_OUT=，默认 <out 去扩展名>_sub.png），环境变量 KEYS='Up=45,Right=2'（依次按住 N 秒）、 SETTLE=（副屏文字每 30 帧才刷新，键盘图至少 12）。 键盘驱动的图必须 SCREEN=both：--disable-limiter 下"按住 N 秒"走多远随机器负载变（实测同一条 KEYS 四次落在 z −3003/−2997/−3054/−2988，三下短按 A 只收到 2 下 —— 逐条记录在 evidence/eye/manifest.txt:246-249）， top 与 sub 分两次跑就是两次不同的会话 ⇒ 读数描述的不是那张画面，编译期孪生必然对不上（本轮真那样 FAIL 过四轮）。both 保证画面与读数同一瞬间， 之后 bash tools/walk_pose_proof.sh 自己读数、按读数建孪生、逐字节比（0/49152 才算这张行走图的站位机位被证明）。

变体纪律：blocksds 的 Makefile 只转发上面这些白名单变量，且 CFLAGS 不是 make 依赖 —— 每个变体必须 rm -rf build/<NAME> 后单独传 NAME=，并且先核对产物 md5 变了再看它的输出。历史上踩过一次：加了 PROJDUMP 却忘了加转发行，镜像与上一个变体逐位相同，打印从未生效。

发布：站上只有两个目的地，且都从同一份上游生成，没有第三份手抄。Qoder Site 走 base:'/'（私有， web/site/dist/）。GitHub Pages 是子路径部署，所以用 SITE_BASE=/nds-site/ npm run docs:build 单独构建一份： 该环境变量同时把 cleanUrls 关掉 —— Pages 只认实体文件，/nds-site/progress 这种无扩展名 URL 必然 404， 只有 .html 形式能用。这份产物推到公开仓库 adam-ikari/nds-site（只有构建物 + .nojekyll， 无源码、无 ROM、无 external/），仓库必须 private:false —— 免费 plan 的私有仓库开不了 Pages。 两个目的地互不污染，判的是导航与资源 URL 而不是字符串本身（正文要提这个前缀，裸 grep 必然自己抓自己）： 私有站那份 dist 的 7 个 html 里 "/nds-site/ 形式命中 0，子路径构建里 7 个 html 全部带前缀， 量具 python3 tools/gen_site.py --check-dist（夹具：正例含一句正文提及 + 一条把 src 改成带前缀的反例）。 两份构建的先后顺序是有代价的：docs:build 把 dist/ 当成唯一输出目录，Pages 那份会原地覆盖私有那份， 所以流程只能是「私有档 → 发布 → 子路径档 → 推 → 立刻重建私有档 → 再跑一次 --check-dist」， 中间任何一步停下来留下的都是错味的 dist。 构建日志本身也要读，不能只看退出码：本轮想把子路径构建挪到 cp -a 出来的副本 + 软链 node_modules 里做 （怕污染真 dist），结果那次 vitepress build rc=0 却吐了 54 处 vitepress data not properly injected in app， 而原地构建两种档位都是 0 处（那 54 处的取法与"先删 .vitepress/cache 仍 54"的对照记在 brain 页 progress-site-single-upstream；盘上此刻还能复核的是反面 —— web/site/.vitepress/build.log 现读该串 0 处命中）。 所以 npm run docs:build 现在把日志落到 .vitepress/build.log 并用 ! grep -q 'vitepress data not properly injected' 挡住 —— 命中就不做后面的 cp -a .vitepress/dist dist，整条链 rc=1。 功率是拿那个副本实测的：vitepress build 自身 rc=0、日志 54 处命中 ⇒ 守卫拦住（先删 .vitepress/cache 再建， 仍是 54 处，所以病因是"在副本里建"不是缓存陈旧）。⇒ 结论：别在副本里建，两份产物都必须在 web/site 原地建。 站点字节刻意不列入逐位复现名单，这条是实测出来的而不是猜的：同一份上游连做两次默认构建， diff -rq 报 7 个 html 全部不同，app.*.js/theme.*.js/@localSearchIndexroot.*.js 三个 chunk 的文件名哈希也换了一遍 —— 本地搜索索引把 lastUpdated 时间打进 chunk 内容，文件名哈希级联跟着变。所以门里那 33 台逐位复现只算 ROM 与截图， 站点的可复现锚在上游：tools/gen_site.py 从 docs/scene-port.md 与 evidence/ 再生那四个页面，字节层不承诺。
